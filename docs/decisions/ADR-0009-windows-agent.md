# ADR-0009: Windows Server Agent and Native Adapters

- Status: Accepted (Phase 05)
- Context: Phase 05 adds a Windows Server agent with native adapters (SCM service control, Event Log reading, host metrics/facts) while keeping the gRPC contract backward-compatible, the control plane a modular monolith, and the security posture identical to the Linux agent (ADR-0002/0003/0005/0008): outbound-only mTLS, typed allowlisted operations, a separate privileged broker, capability-gated features, full audit, NO shell strings and NO arbitrary command execution.

## Decision

1. **Same agent core, per-OS adapters.** The agent module keeps one run loop (`internal/agent/run.go`), one store, one protocol client. OS-specific behavior is isolated behind build tags: `detect_linux.go`/`detect_windows.go` (osdetect), `collect_linux.go`/`collect_windows.go` (metrics), `registry_unix.go`/`registry_windows.go` (executor registry), `daemon_unix.go`/`daemon_windows.go` (server-privd). Cross-platform schemas, validators and pure parsers live in `internal/winops` so they are unit-tested on EVERY GOOS (CI: ubuntu, debian, windows).
2. **Privileged broker on Windows = named pipe + SID allowlist.** `server-privd` on Windows runs as LocalSystem and listens ONLY on `\\.\pipe\server-control-privd` with SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)` plus the agent account's SID. Caller identity is KERNEL-VERIFIED via `ImpersonateNamedPipeClient` + thread-token `TokenUser` SID (no PID-reuse race); the agent client opens the pipe with `SECURITY_SQOS_PRESENT|SECURITY_IDENTIFICATION`, so the broker can identify but never act as the caller. The allowlist (`--allow-sid`) is explicit, default-deny, and audited on every rejection — the exact trust model of the Linux Unix-socket broker (SO_PEERCRED UID allowlist). Non-pipe transports are REJECTED in `identifyPeer` (the Faz 04 test fallback was removed; IN-01 fixed).
3. **SCM via x/sys, not sc.exe.** Service list/status/start/stop/restart use `golang.org/x/sys/windows/svc` + `svc/mgr` structured APIs opened with LEAST privileges (`SC_MANAGER_ENUMERATE_SERVICE|CONNECT` for listing). Stop is a `svc.Stop` control followed by a bounded state poll; restart is stop→start (non-idempotent, retry-unsafe, mirrors systemd restart semantics). Windows service KEY names are allowlisted (`^[A-Za-z0-9][A-Za-z0-9 ._-]{0,79}$`, no trailing dot/space) at THREE layers: control-plane validator, agent executor, broker `validateRequest`.
4. **Event Log via wevtutil argv with a FIXED template.** `windows.eventlog.read` executes `wevtutil query-events <channel> /count:N /rd:true /format:xml` — the channel is a closed enum (`Application|System|Setup`), counts are bounded ints (1..200), and NO XPath/query text is ever composed from input; level filtering happens client-side. Output is parsed with `encoding/xml` into bounded events (message one-line, ≤4000 bytes, ≤200 records). The Security channel is deliberately EXCLUDED (needs admin; sensitive). The agent runs this DIRECTLY (no broker hop) — the read-only channels need no elevation.
5. **NO PowerShell execution surface — by design.** There is no PowerShell endpoint, no `powershell.exe`/`pwsh` argv path, and no generic command execution anywhere in the agent or broker (ADR-0003 holds on Windows too). The support matrix below documents this as a permanent refusal, not a missing feature.
6. **Metrics/facts via Win32 with zero new dependencies.** Facts read the registry (`CurrentVersion`: ProductName/DisplayVersion/CurrentBuild+UBR). Metrics use `GetSystemTimes` (CPU window %), `GlobalMemoryStatusEx` (memory), `GetDriveType`+`GetDiskFreeSpaceEx`+`GetVolumeInformationW` (FIXED volumes only), `GetIfTable` (network counters; explicit MIB_IFROW offsets, fixture-tested on all GOOS), `GetTickCount64` (uptime). Everything comes from `golang.org/x/sys/windows` (already a pinned direct dependency, BSD-3-Clause) — no new module is introduced in Phase 05.
7. **The agent itself is a native Windows service.** `server-agent svc-run` implements `svc.Handler` (StartPending→Running→StopPending, AcceptStop/AcceptShutdown) so SCM launches/controls it natively; `server-privd` detects SCM context and runs the same way. Installation is documented with plain `sc.exe` commands (no install scripts that would need signing).
8. **Server-side integration is additive.** Six new operation specs (`windows.scm.service.{list,status,start,stop,restart}`, `windows.eventlog.read`) are registered with payload validators; SCM reads require `service:read`, SCM control `service:control` (SAME risk class as Linux — reused, not re-invented), event-log read gets a NEW `eventlog:read` permission seeded to admin+operator by migration 0009 (granting ONLY the new permission — the CI-04 lesson). No proto change: capabilities, facts, metrics and task dispatch flow through the existing v1 contract (buf breaking gate enforces backward compatibility).

## Consequences

- Support matrix: Windows Server 2019/2022/2025, amd64, agent+broker as native services; `windows.scm.service.*` requires the broker (LocalSystem); `windows.eventlog.read` covers Application/System/Setup only; Security channel and package management are NOT implemented (honest capability reporting with reasons).
- Real-Windows verification happens in the new `agent-windows` CI job (windows-2025 runner: SCM read-only, real named-pipe allow/deny, wevtutil System probe, Win32 metrics smoke, registry facts); destructive service control is mock-tested only. Owner verification on a disposable Windows VM follows `deploy/agent-windows/README.md`.
- Named-pipe deadlines are close-timer based (sync pipes have no kernel deadlines); bounded by the existing call timeouts. Pipe ACL is validated in CI via allow/deny SDDL variants.
- The Faz 04 audit contract is unchanged: one JSONL line per handled request (rejections included), written BEFORE the response; on Windows the file lives under `C:\ProgramData\server-control\` and rotation is delegated to the operator (journald/logrotate equivalent: Windows Event Forwarding or scheduled task + log rotation).
