# ADR-0020: İmzalı Güncelleme Hattı — Staging, Zorunlu İmza+Hash Doğrulaması, Health-Check ve Rollback

- Status: Accepted (Phase 15)
- Context: Sürüm politikası ("Agent auto-update must be staged, signature-verified, health-checked and rollback-capable. Never self-update a privileged component from an unauthenticated URL") ve tehdit modeli, imzasız güncellemeyi **release blocker** sayar. Agent ayrıcalıklı broker ile kök yetkisi kullanır; bozuk/kötücül bir ikiliğin yerine geçmesi node'un tamamını ele geçirmek demektir.

- Decision:
  1. **İmza şeması (SCP-SIG-V1, yalnız stdlib):** tüm sürüm artifact'ları (Linux deb/rpm, Windows zip, update paketleri) için ed25519 imzası, **kanonik bayt dizisi** üzerinde hesaplanır: `scp-sign-v1\n` + `<dosya adı>\n` + `<boyut>\n` + `<sha256 hex>\n`. İmza base64; doğrulama `sigtool verify` ile. Güven kökü: repoda yayınlanan **genel anahtar** (_release.pub_), özel anahtar sürüm yöneticisinde (depoya ASLA yazılmaz). Agent/broker tarafında güven kökü `--update-trust-key` (base64 ed25519 genel anahtarı) ile verilir.
  2. **Node güncelleme akışı (update.* ailesi, `--update-enable` VARSAYILAN KAPALI):**
     - `update.stage`: payload `{update_id, version, sha256, signature}` — agent, operatörün yerleştirdiği paketi **yerel** staging dizininden okur (payload'da yol ALANI YOK — yüzey genişletemez); önce SHA-256, sonra imzayı doğrular. Herhangi biri başarısızsa tipli red (ErrHashMismatch/ErrBadSignature) ve staging **yapılmaz**. Doğrulanan paket `/var/lib/server-control/updates/staged/` altına taşınır; durum `update.status` ile raporlanır.
     - `update.apply` (bu fazda stage ile birleşik apply adımı değildir): yeni ikilik kurban (rollback) kopyasına ayrılır, staging ikiliği hedefe atomik (rename) yazılır, health-check = hedef ikiliğe `--version` çalıştırma + çıkış kodu/sürüm karşılaştırması; health başarısızsa **otomatik rollback** (kurban geri) ve tipli hata. Aktivasyon (çalışan servisin yeni ikiliği alması) systemd/broker yeniden başlatması ile olur — belgelenmiş operatör adımı; `service.restart` mevcut tip işiyle yapılabilir.
     - `update.rollback`: kurban ikiliği geri yükler; health-check aynı disiplin; audit ve sonuç şeması zorunlu.
     - `update.status`: staged/active/rollback sürümleri + son health-check sonucu (read_only).
  3. **Windows:** ikilik değişimi kilitleme farklıdır (çalışan .exe yeniden adlandırılamaz). RC'de Linux'ta tam lifecycle kanıtlanır; Windows'ta update ailesi aynı şema ile doğrular, **stage** yapar ve aktivasyonu SCM dur/dosya değişimi/başlat operatör prosedürüne bırakır (deploy rehberi). Dürüst sınırlama olarak raporlanır.
  4. **Control Plane kendi kendini güncellemez:** CP yükseltmesi, imzalı artifact + `control-plane verify-update` doğrulaması + **önce yedek** (Faz 14 `backup.cp.run` + doğrulama) + migration sınırlamaları belgelenmiş prosedürle operatör tarafından uygulanır. Hiçbir HTTP ucu uzaktan CP ikiliği değiştiremez (ADR-0003).
  5. **Uyumluluk:** update manifest'i `min_prev` (geçerli önceki sürümler) ve `api_version` taşır; uyumsuz düşürme/yükseltme staging'de tipli reddedilir. Sürüm düşürme (downgrade) paket düzeyinde belgelenmiş sınırlamalara tabidir (veri şeması geriye uyumsuzlukları) — release dosyasında listelenir.
  6. **Depolama/RBAC:** CP tarafında `update_artifacts` tablosu (hedef platform, sürüm, sha256, imza, min_prev, durum staged/published/revoked). Yayınlama (`updates:control`) imzayı CP'de de doğrular — imzasız artifact kayıt bile edilemez. Node görevleri `updates:control` + `tasks:write` ister; broker ailesi opt-in'dir.

- Consequences: "İmzasız veya hash doğrulaması başarısız update reddedilmeli" kriteri üç katmanda uygulanır (CP yayınlama, agent staging, health-check + rollback). Güven kökü tek anahtardır (RC); anahtar rotasyonu ileri çalışmadır ve ADR revizyonu gerektirir. Yerel-staging modeli (agent internete çıkamaz) Faz 00'dan beri sabit bağlantı kısıtıyla uyumludur.
